二、逐项整改
1. 数据库迁移与初始化
复用上一轮固定版本/校验和清单、缺失/额外/乱序/冲突拒绝策略及生产/预生产共同迁移入口，保留所有旧迁移校验和。仅追加 173_r3_security_scope_and_sessions.sql，候选版完整链为 172 条原迁移加 1 条安全迁移，共 173 条。新代码通过只读 security_schema_status 视图核对必需迁移版本及校验和，缺少/不匹配时拒绝启动，防止漏迁移后运行。

2. 角色管理
新增统一服务端授权模块 management-security.cjs。事务取得账号授权锁后，重新核验会话、CSRF、当前权限和角色，不能使用等待前的登录快照。受限人员不能修改自身角色、内置岗位或跨范围使用的角色；只能管理权限不高于本人、且所有关联账号均在其完整授权范围内的自定义角色。创建/复制/模板建角色和改权限都使用同一授权上限。不能通过相同权限字符串切换不同内置岗位来取得岗位专属能力。
内置岗位按现行 role-catalog.builtins 与历史 built_in 标记共同识别；发现部分销售岗位历史标记为 false，已先证明绕过，再改为以现行目录兜底识别，未改写历史角色数据。系统管理员仍能维护各内置岗位权限，保留 users:manage、roles:manage 恢复能力；内置岗位名称保持固定。

3. 账号管理
列表、详情/删除预检、编辑、密码重置、删除和恢复统一要求“覆盖目标账号的全部范围”，不以一个项目重叠作为通过条件。受限人员不能操作管理员、不能管理具有更高权限或跨范围账号，不能自升角色。新建/变更/恢复的角色也必须在本人授权上限内。非管理员分配内置岗位时仅允许本人同一内置岗位，其余由系统管理员分配。
大写 UUID 自身角色绕过已先用失败测试证明，再改为比较数据库返回的规范 ID。合法范围内的新建、编辑、重置、软删除和恢复通过；用户 ID、历史单据引用和审计记录保留。
注册申请没有可靠项目归属。经用户明确确认：待审申请队列及审批仅系统管理员可用；受限人员仍可在范围及授权上限内新建普通账号。前端同步隐藏受限账号的注册审批入口，后台接口同样拒绝。

4. 审计范围
旧 /api/v1/audit 与新 /api/v1/v27/audit 列表、数量、详情共用同一范围谓词。具有 audit:read 的系统管理员保留全局审计；普通角色必须覆盖事件快照中的全部项目/仓库/客户范围。多范围事件只覆盖一部分仍不可读。
追加 audit_logs.scope_context，插入触发器从白名单实体及事件时载荷生成不可改写的范围快照；忽略调用者伪造的快照，不按办理人当前范围或实体当前归属重新归类旧日志。UUID 规范化以免合法大写 UUID 被误判为未知。
173 以前没有新范围快照的历史行不回填、不猜测，按未核实处理，仅系统管理员可见。系统类、无法核实或维度不足的事件采取保守限制；缺少仓库/客户精度时需要相应上层完整范围。此限制是安全整改的有意收紧，没有删除或改写任何历史日志。

5. 会话与并发
管理写事务取排他授权锁后重查会话、CSRF、当前角色/权限与范围。新增数据库触发器，使角色权限、账号角色/状态/密码以及数据范围变更撤销相应全部会话，其他用户不受影响。
普通已认证写请求使用独立连接池持共享授权锁，业务处理完成后释放；撤权与业务写入按同一边界序列化。已开始的业务写入先结束，撤权才能提交；尚在等待授权的请求解除等待后重新检查会话，不能携带旧授权写入。不是强行中断已执行的 SQL。管理写及语言偏好使用专门的锁顺序，避免自身共享/排他锁升级死锁。
授权连接池与业务连接池分开，已覆盖超过池大小的 24 并发写请求。池大小为 min(DB_POOL_MAX,10)，业务池仍用原 DB_POOL_MAX，上线前需核算每实例两池的总连接预算。

2. pnpm test

4. 设置 WMS_TEST_OWNER_URL（独立 TEST 服务管理连接，以 /postgres 结尾）、WMS_TEST_APP_PASSWORD。管理角色需要 CREATEDB；若尚未预建 musonoi_app，还需要 CREATEROLE。测试只新建 musonoi_audit_<随机值>_test，不覆盖已有库。
